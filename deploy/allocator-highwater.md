# Identity allocator checkpoint

Native `IDENTITY_DATA_SOURCE=identity` requires the independent `identity-allocator-schema.sql` asset and a verified ready checkpoint before the one-way authority transition. Legacy mode does not require the checkpoint or table. This asset adds one private table and never activates authority or changes a sequence. The previous nine schema assets remain unchanged.

Reviewed asset SHA256: `53c591414b31b1fe259eff08fbe89f1fb1ceb83ea8aa227315337cede0ad647f`.

A migrated database must retain the source AUTO_INCREMENT highwater, actual source and target ID capacities, and all reviewed historical references. The six source allocators are `user`, `user_info`, `organization`, `wechat`, `invitation_record`, and `invitation`. `user` is also capped at the signed INT range of existing business projections. Historical deleted/tombstoned accounts, mappings, expired or revoked sessions, cutoff rows, profile archives, organization maps and retained business references all reserve IDs. IDs are canonical decimal strings and are compared with BigInt. Private local event sequences have no invented source counterpart.

## Migrated development database

Keep native HTTP off. Prepare the new checkpoint asset separately. The production CLI only accepts direct `10.206.0.5:3306`, readonly source `bujiaban_development`, target `xrugc_identity_dev`, and the existing private principal `identity_dev`; credentials come from current config and are never printed. Source SELECT permission is not evidence that source writers have stopped.

1. Before the final window, obtain schema/reference evidence with `node dist/scripts/allocator-highwater.js --inventory`. This performs readonly inventory and does not create proof or change counters.
2. Actually hold every old account, provider, PHP, session and reconciliation writer. Keep that hold through activation. Run final account sync and all approved binding/session/challenge imports. Then run `node dist/scripts/account-sync.js --dry-run --max-changes=100000` and save the complete original JSON report in a protected 0600 file. It must contain the exact AccountSyncReport fields, all five counters zero and empty tableChanges. Any subsequent mutating import invalidates ready; account-sync apply does so even with zero deltas. Pure readonly dry-run and exact replay do not invalidate.
3. Prepare a reviewed 0600 JSON file with exactly `version:1`, `sourceDatabase`, `targetDatabase`, `sourceServerUuid`, `importKey`, `writersDrainedAt` (ISO UTC milliseconds), `finalSyncSha256` and `referenceReviewSha256`. Use the source UUID/reference digest actually returned by inventory, the existing account import key, and the SHA256 of the exact final zero-sync report. The reviewer must independently verify the real writer hold; hashes cannot manufacture this fact.
4. Default read-only plan: `node dist/scripts/allocator-highwater.js --review=/protected/review.json --review-sha256=<exact file SHA256> --final-sync-report=/protected/sync.json --report=/protected/new-plan.json`. The tool validates the protected files and reruns the existing zero-delta sync on the exact current connections. The report destination must be new. All operator inputs/reports/journals stay protected; stdout contains only status and digests.
5. Apply with the same arguments plus `--apply --journal=/protected/new-journal.jsonl`. The tool independently holds the staging fence across DDL implicit commits, first durably marks pending while retaining previous evidence, and only raises the six AUTO_INCREMENT counters. Each DDL intent and successful readback is fsynced. Source metadata and current reference values are rechecked outside the old RR snapshot before, during and after the sequence changes. Partial success or uncertain results stop without retry, cleanup or lowering counters. Inspect evidence, then make a new reviewed plan; never replay a failed SQL blindly.
6. Only a complete readback creates ready. Native bootstrap locks the same authority fence, checks strict manifest/digest/import-source binding, current private references and counters, then activates. It never reconnects to the old source or alters a sequence. The source UUID is provenance; target server UUID is not pinned, so legitimate managed database failover does not invalidate proof. Normal later native growth is allowed, while counters below the persisted floor or current retained references reject restart.

The library accepts random local fixture schemas so tests can perform actual account imports and finalization without special ENV proof bypasses. The production CLI and the native `xrugc_identity_dev` target enforce the fixed development source.

## Explicit fresh installation

Install all formal native assets first, then run `node dist/scripts/allocator-fresh.js --apply --database=<exact configured private database>`. This separate installer uses only the configured private connection and cannot infer fresh from an empty user table. Every formal table must exist; every actual historical namespace must be empty; all counters must be pristine; only the four official role seeds, migration staging row and event clock row are permitted. Existing proof cannot be overwritten. A staging fresh checkpoint is rechecked for emptiness under the activation fence. Once authoritative, valid native growth passes subsequent restarts.

## Authority and rollback

Ready proof is not activation authorization. No command here starts HTTP, changes business credentials, grants privileges, imports unreviewed providers, or switches clients. Keep applications on Identity authority during an application rollback. Restoring an old private snapshot or changing the data-source flag cannot reverse the persistent authority fence; changing account authority requires a separately reviewed freeze and reverse migration preserving all newer users, password changes, sessions and revocations.
